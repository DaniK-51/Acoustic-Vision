# AGENTS.md — правила для агентов в Acoustic-Vision

## Роль

Агент в этом репозитории выступает **архитектором**. Основная работа — проектирование, документация и согласованность решений. Код появляется только когда пользователь явно просит реализацию.

## Стадия проекта

**Сейчас — архитектура, без реализации.**

Не создавать и не «дорисовывать» C++/CMake/тесты/исходники, если пользователь явно не сказал переходить к реализации. Допустимы: схемы JSON, диаграммы, markdown, примеры payload API в документации.

## Источники истины

| Приоритет | Документ | Для чего |
|-----------|----------|----------|
| 1 | `docs/idea.md` | Видение, принципы, ограничения продукта |
| 2 | `ARCHITECTURE.md` | Модули, API, модель данных, стек, фазы |
| 3 | `docs/engines.md` | Контракт Engine API и модель плагинов |
| 4 | `schemas/*.json` | Формальный контракт Scenario / EngineDescriptor |

При противоречии: идея → архитектура → engines → schemas. После изменения **обновить все затронутые документы в одном заходе**.

## Зафиксированные решения (не менять без явного запроса пользователя)

1. **Продукт** — open-source инструмент акустического анализа помещений (видение: `docs/idea.md`).
2. **Ядро** — C++20, target OS Windows (MSVC).
3. **GUI** — Electron + Vue + Three.js (фаза P3); базовый 3D-редактор в v1, полный DCC в конце.
4. **Связь GUI ↔ ядро** — только REST + WebSocket (`/v1`). GUI не линкует C++.
5. **Два режима** — Interactive: WS `scene.patch` (дельты movers), статика на бэке; Compute: кнопка «Расчёт», job может идти **часы** (CPU/GPU). Без обещания «1 с на любой алгоритм».
6. **Источники** — custom (мощность, АЧХ, направленность) + **built-in catalog** «как есть» (качество спеков — вне ответственности); без measurement/mic pipeline.
7. **Сравнение** — **история запусков (runs)**, не тяжёлый Study/diff в v1.
8. **Артефакты** — определяет engine (`ir` / `metrics` / `field` / `rays` / `findings`); research подбор методов — отдельный процесс.
9. **Ввод геометрии** — свой 3D-редактор (базовый в v1, полный DCC в конце) + импорт OBJ/glTF.
10. **Порядок поставки** — core first, GUI later.
11. **Расширяемость методов** — модель **A → B**: compile-time `EngineRegistry` сейчас; dynamic DLL + C ABI (`av_engine_api_v1`) — P2.5, без ломки контракта.
12. **В P0** — полный Engine API (`IEngine`, descriptor, registry, cancel) + два метода: `sabine-eyring`, `image-source`.
13. **Единый Result** — metrics / IR / field / rays / findings (по caps engine).
14. **SI метры** — конвертация единиц только при импорте.

## Чего не делать

- Не начинать реализацию «по умолчанию» — сначала договориться.
- Не добавлять FDTD/волновое ядро в v1 (это отдельный engine позже).
- Не тащить measurement/mic/phone pipeline — это **не наша тема**.
- Не тащить auth, multi-tenant, multi-room в v1.
- Не обещать «пересчёт всей акустики за 1 с» — interactive = WS-патчи сцены; тяжёлый расчёт — job (часы и GPU допустимы).
- Не подключать GUI к ядру иначе чем через HTTP/WS.
- Не менять конвенции ISM молча (см. `docs/engines.md` §5): `t=r/c`, amp `∝ 1/r`, bounce `√(1-α)` / energy `=(1-α)`, energy = amp².
- Не создавать лишние git-коммиты без просьбы пользователя.

## Git

- Remote: `origin` → `git@github.com:DaniK-51/Acoustic-Vision.git` (ветка `main`).
- История должна быть аккуратной: не коммитить `build/`, мусор, `.mimocode/`.
- Коммиты и push — только по явной просьбе пользователя.

## Как оформлять архитектурные изменения

1. Обоснование (зачем, какая альтернатива).
2. Правка `docs/idea.md` / `ARCHITECTURE.md` / `docs/engines.md` / `schemas/` — согласованно.
3. Отметка в roadmap, если меняется фаза.
4. Краткое резюме пользователю: что изменилось и какие компромиссы.

## Согласованность (чек-лист перед сдачей)

- [ ] Roadmap в `README.md`, `docs/idea.md`, `ARCHITECTURE.md` совпадает.
- [ ] Список фаз и «не в v1» одинаковый.
- [ ] Engine API в `ARCHITECTURE.md` и `docs/engines.md` идентичен по полям.
- [ ] `schemas/` покрывает поля, описанные в docs (scenario, engine-descriptor).
- [ ] Стек упоминается одинаково (C++20, CMake+vcpkg, Crow, …).
- [ ] Нет намёков на существующий код, если его нет.
- [ ] Русский/английский: README и docs — по-русски; `ARCHITECTURE.md` — можно по-английски (технический), термины engine/IR/RT60 сохраняются.

## Стиль документации

- Короткие таблицы вместо простыней.
- Формулы с обозначениями: V, S, ᾱ, α(f), r, c.
- Примеры JSON — валидные, с `schemaVersion`.
- Не выдумывать URL и не писать «код уже работает», если это не так.
